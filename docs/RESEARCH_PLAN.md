## 1. The question

**When does training-free block-sparse prefill actually pay end to end on a given host CPU and GPU, and can that be predicted before timing the workload there?**

- **RQ1.** Can component measurements predict end-to-end prefill time, and the sparse-versus-dense crossover, on a pairing on which the workload has not been timed? (H1, H2, H3) No timing of the workload on the target is an input to its prediction; the operation order and the estimator's selection are recorded per code path, on the target when its code path is new, with every duration discarded (Section 5.1).
- **RQ2.** Does keeping the execution order and position of each estimator's host work and synchronisations improve that prediction over aggregate models? (H1 against the KernelSight-style step form and the fitted sum; the XAttention pair, where XAttention is Xu et al., "XAttention: Block Sparse Attention with Antidiagonal Scoring", ICML 2025 (Proceedings of Machine Learning Research, vol. 267, pp. 69819-69831, <https://proceedings.mlr.press/v267/xu25ag.html>); arXiv:2503.16428; code `mit-han-lab/x-attention`, used at commit `e379887`, installed and called, with the lines listed in `docs/vendor_register.md` reproduced)
- **RQ3.** At matched per-layer recall, is accuracy the same whichever estimator chose the blocks? (H4)
- **RQ4.** Do the model's predictions, combined with the admissible density, decide whether to use sparse prefill on an unmeasured pairing better than the decision suggested by kernel speedups? (H6)

Papers report sparse attention kernel speedups on one or two machines. Our own measurements show the kernel speedup often does not survive end to end. On an A100 with our reference mask builder, prefill became slower (0.63x to 0.75x) although the sparse kernel beat PyTorch's SDPA flash kernel. How much of the builder's loop time was Python overhead depends on the instrument: about 94% under `cProfile`, which files the loop's tensor element writes under Python time, and about 53% under `torch.profiler`, which counts them as operators (development-machine profiles at 32768 tokens, not banked; T2.2 re-measures both on the target host). A vectorised builder turned the A100 result into a speedup; against the fastest correct dense kernel the speedup is smaller still, and at 8192 tokens it becomes a loss (Section 2). So host-side cost is not fixed: it depends on how an estimator is implemented. What remains when masks are built on the GPU is host-visible work and GPU-to-CPU synchronisation. Released research code still reads GPU values from Python: XAttention runs two `assert` checks on GPU tensors per query chunk in every layer, and the FlexPrefill implementation bundled with it sizes index tensors with `.max().item()`. Compilation does not remove all of these by default: under `torch.compile` with default settings, `.item()`, `nonzero()` and an `assert` that turns a tensor into a Python bool (such as `assert not t.any()`) each break the graph, while a plain `assert` on a tensor (rewritten into `torch._assert`) and a fixed-size `topk` do not (CPU, PyTorch 2.8.0 and 2.14.1; `results/compile_graph_breaks_cpu/`, `scripts/check_compile_graph_breaks.py`). XAttention's prefill path uses the plain form (upstream commit `e379887`, `xattn/src/utils.py`), one of the two inside a `try`/`except`; the plain form did not split the graph on a CPU, and the `and` form, which splits, is on the decoding path only. Whether the compiled code still makes the GPU wait for them is measured under T2.21. Compiled arms measure what remains on the GPU (Section 5.5). Whether sparse prefill pays therefore depends on the host, the GPU, how their work overlaps, which synchronisations an implementation makes, and whether the sparse masks keep accuracy.

**Contributions, in order of weight.**

- **G2 (lead). The cost of data-dependent sparsity.** Sparse attention keeps different blocks for every input, so an implementation must read sizes or checks back to the host (a synchronisation), pad to a worst case (extra GPU work), or work in fixed-size buffers (a fixed budget). G2 is a per-operation critical-path model of the order and position, *within* a prefill step, of each estimator's data-dependent host work and GPU-to-CPU synchronisations (mask building wherever it runs, data-dependent sizing, checks that read GPU values), built only from measured components. It prices synchronising and fixed-size implementations on a given pairing; where an implementation pads, the padded work is part of its device cost. Aggregate models, including KernelSight-LM's step formula, do not represent where in a step these fall (Section 3). It predicts what each synchronisation costs on a given pairing, and so what removing it would gain, before anyone builds a fused kernel. Arms without synchronisations, including compiled arms with no wait left, are part of the test: on them the model should add nothing over simpler forms. **Not claimed as new:** the host-cost measurement method, which adapts TaxBreak's null-kernel protocol (TaxBreak uses null kernels for the launch path; we substitute them across the whole operation sequence and measure host-side compute directly at target sizes), and the queue-aware recursion, which is a standard form of host-device overlap. The adaptation is not claimed as a contribution. What is new is placing data-dependent synchronisations within the step and predicting their cost on pairings where the workload has not been timed.
- **G3 (lead).** A test of whether attention recall is an estimator-independent proxy for accuracy: at matched per-layer recall, does accuracy depend on which estimator chose the blocks? This is tested, not assumed. Prior evidence points both ways: within its own indexer, VSPrefill finds accuracy indistinguishable from full attention above 90% recall and calls recall "a faithful surrogate objective"; in decoding, Less Is More argues that which tokens are kept (a stable recency window) matters. Either outcome of H4 is reported.
- **Application: a profitability dispatcher (RQ4, H6).** For each pairing, context length and batch, the dispatcher uses the predicted time and the admissible density to choose dense or a sparse arm at a density, before the workload is timed on that pairing (Section 5.9). It is scored by regret against the best measured choice and compared with the decision suggested by kernel speedups. It answers the question a practitioner faces on a given host and GPU: should sparse prefill be switched on at all?
- **G1 (validation question).** Whether this explicit model predicts end-to-end time on real, physically distinct host-GPU pairings better than a learned predictor when only a few hardware systems are available for training. Cross-device latency prediction itself is not new (CTFusion), so G1 is not claimed as a new problem. The fitted sum (Section 5.4) is the primary comparison for G1; the learned predictor is secondary.

**Name.** The method is named BUNGA (Block-sparse Utility Navigator for GPU Attention), made of the G2 critical-path model (components defined in Section 5.1, the recursion in Section 5.4) and the profitability dispatcher (Section 5.9), while `attnbench` remains the name of the measurement harness.

**Scope.** One GPU, one CUDA stream per forward pass, batch 1 and 4, PyTorch eager and compiled. Claims do not extend to multi-GPU, continuous batching or multi-stream serving engines; the abstract states this.

**How the two halves connect.** "Profitable" (Section 5.1) needs both a speedup and non-inferior accuracy. Predicting it on an unmeasured pairing therefore needs two things: end-to-end time at a given density (G2, RQ1 and RQ2) and the lowest density at which each estimator keeps accuracy. If H4 holds, that density can be read from recall, which is cheap to measure and does not depend on the hardware; combined with the time model, profitability on an unmeasured pairing is then predicted with no accuracy runs at all. If H4 fails, each estimator needs its own accuracy runs, and the study reports where recall falls short. Either way the result is one pipeline: predicting when sparse prefill pays (T7.6). The dispatcher (Section 5.9) turns that prediction into a decision and scores it (T7.7).

**If sparse prefill never pays.** In the pilots no deployable estimator was non-inferior at any tested density, so the profitable set may be empty on every pairing. That is stated in advance as a possible result, not a failure. The claims then are: predicted against measured end-to-end time and crossover per pairing and arm (RQ1, RQ2); which operations and synchronisations keep each arm from paying, and by how much on each pairing; whether the dispatcher avoids the losses the kernel-speedup rule would make (RQ4); and the recall result (RQ3). The paper's title would then name prediction, not profitability.

**Target.** An IEEE Transactions-level journal (TC, TPDS, TCAD or ACM TACO; open, see Section 11). Nothing here claims that bar is reached.

## 3. Gaps and nearest work

| Gap | Statement | Nearest work (read in full unless marked) |
|---|---|---|
| G1 | Learned cross-device predictors exist (CTFusion: 20 training systems, host side is input preprocessing). KernelSight-LM measures host constants per host and states that they "depend on the host CPU and serving engine, not on the GPU" (its Section 5.7), without testing it; its Section 5.5 calls them properties of the host, GPU and engine together, yet re-measures them only when the host or serving engine changes. Untested: whether an explicit critical-path model of measured components predicts data-dependent sparse prefill better than a learned predictor when few systems are available. | CTFusion, KernelSight-LM, CloserToMe; nn-Meter, HELP (abstracts only) |
| G2 | Host-overhead summaries (TaxBreak's HDBI, SKIP's TKLQT) are ratios or sums. TaxBreak splits host-visible time into framework, library and launch-path parts, and we adapt its null-kernel protocol to measure host costs (null kernels across the whole operation sequence rather than the launch path alone); it does not compose those costs in execution order with synchronisation positions, and the gap between the KernelSight-style step form (our baseline) and the recursion measures what that composition adds. (TaxBreak's remark that host cost is often shown "only as an aggregate residual" describes earlier work, not TaxBreak.) KernelSight-LM (read in full) composes within a step by one formula: the larger of GPU time plus dispatch and a term ℓ that the paper does not define, plus any excess of the host overlap floor over GPU time, plus a serial tail (its Section 5.7, Eq. 4); its discrete-event scheduler advances one event per batch step (Section 4.2), so nothing records where in a step a synchronisation falls, and its synchronisation term is tensor-parallel all-reduce between GPUs. Its Tier B measures host constants on the target with a short serving sweep. Serving simulators (LLMServingSim 2.0, the APEX simulator) work from per-device profiles and model no host work inside a step. TaxBreak says its replay can be imperfect for synchronisation-heavy kernels. Fused GPU kernels can remove host work and synchronisations (VSPrefill merges indices inside its kernel); released estimators often still make them. HiSparse (decode, not prefill) fuses each layer's KV-cache miss handling into one kernel inside the decode CUDA graph, which it says requires no host-side branching; it picks its cache size by profiling sweeps on each platform and finds the best setting depends mainly on host-link bandwidth. It is a system design, not a predictive model. Compilers do not remove data-dependent synchronisations by default: `torch.compile` breaks the graph at `.item()`, `nonzero()` and some forms of tensor `assert` (Section 1); whether its capture options remove the wait on the GPU is measured by the compiled arms. No lightweight model places data-dependent host work and synchronisations inside a prefill step and predicts their cost on an unmeasured pairing. | TaxBreak, SKIP/TKLQT, KernelSight-LM, LLMServingSim 2.0, APEX (Fan et al.), APEX simulator (Lin et al.), VSPrefill, HiSparse |
| G3 | Whether recall is a sufficient accuracy proxy across estimators is untested. The Sparse Frontier lists a narrower question as unknown: "How close a recall-maximising mask is to a task-loss-optimal one" (its Limitations). VSPrefill and Less Is More compare recall across methods, not accuracy at matched recall; VSPrefill's own indexer reaches full-attention accuracy above 90% recall, while Less Is More (decoding) argues that keeping a recency window matters, so prior evidence points both ways. ## 5. Method

### 5.1 Definitions

- **Unmeasured pairing.** A host-GPU pairing on which the workload has not yet been timed when the prediction is written. On the target itself the workload runs only in the structural probe (short contexts, under the profiler; for a chunked arm whose probe result is "different", once more at full length to record its structure), and, if the mask gate fails on the first card of a new code path, in an untimed mask-recording pass; every duration from all of these is discarded (Appendix A, 27 Oct 2026). Allowed inputs, stated the same way for every pairing: microbenchmarks on the target (host components measured on that host without the workload on the GPU, and link and synchronisation microbenchmarks on the pairing, including bandwidth under a mask-sized CPU load; seconds); device components of that GPU; and two functional artifacts recorded per code path with every duration discarded: the operation sequence and the estimator's selection (below). No timing or trace of the composed workload on the target is an input: the claim is prediction without timing the workload on the target, from seconds of microbenchmarks there, not zero-shot prediction. The prediction file and its sha256 are synced before the timed workload starts, and the workload starts more than 60 s after the sync; a session waits 90 s (60 s plus a 30 s margin, so the store's whole-second creation time and the upload never eat the gap); the analysis allows 60 s of clock skew between the store's clock and the instance's and refuses any prediction stamped later; both numbers are `predict/commit.py`'s (Appendix A, 25 and 31 Oct 2026).
- **Host component** c_host(i): host time to issue operation i (framework dispatch, library front end, launch floor) plus host-side compute such as CPU mask building. Measured by adapting TaxBreak's null-kernel protocol, which applies null kernels to the launch path, to the whole operation sequence (device work replaced by null kernels), and by running host-side compute directly at target sizes. The adaptation is not claimed as a contribution.
- **Device component** c_dev(i): GPU execution time of operation i, from replaying the arm's whole kernel sequence in order on the target GPU, with the masks recorded for its code path, as a CUDA graph (primary; keeps cache state between kernels and has no host gaps). Isolated per-operation replay is the cross-check, and the difference between the two is reported as the cache effect. A position the graph cannot hold as recorded (a substitution on the replay tape, such as `nonzero_static` for `nonzero`) is priced from an isolated replay of the original operator, and each position's cost source (graph or isolated) is flagged (Appendix A, 27 Oct 2026). Never from a run of the composed workload: the replay contains no host, link or synchronisation cost.
- **Link component** c_link(i): pairing-dependent copy time of a non-synchronising operation i (a host-device copy the host does not wait for), from microbenchmarks on the pairing, at the loaded bandwidth where the operation sequence puts the copy alongside host-side estimator work. Synchronisations are costed separately (next item), so no physical event is charged twice.
- **Synchronisation.** Any point where the host waits for the GPU: an explicit synchronise, a copy to the host, or Python reading a GPU value (`.item()`, `bool()` of a tensor, an `assert` on a GPU tensor, sizing from `nonzero()`). Each synchronisation is one operation in the sequence and is costed once, by mechanism m: s_0(m, payload) = s_fixed(m) + payload / B. s_fixed(m) is the host cost of issuing and completing mechanism m (explicit synchronise, event synchronise, `.item()`, `bool()` of a tensor, pinned or pageable copy to the host, blocking copy from the host) with the device idle, measured at the smallest payload so it contains no transfer time (Appendix A, 25 Oct 2026). For `.item()` and `bool()` of a tensor the payload is zero by definition, so their s_0 is s_fixed (Appendix A, 25 Oct 2026). B is the copy bandwidth from the same microbenchmark as non-synchronising copies, loaded where the operation sequence puts the copy alongside host-side estimator work and unloaded otherwise, never fitted. The wait itself is never a measured constant: the recursion produces it (Section 5.4). For a synchronising operation l_i = d_i = 0. **Composite mechanisms are split:** an `assert` on a GPU tensor and sizing from `nonzero()` each become a kernel operation, with its device cost from replay, followed by a synchronisation; no operation carries both. An implicit synchronisation inside an allocator call such as `cudaFree` is not costed: it is a trace check, and a prefill trace that shows one is flagged (T2.3; Appendix A, 25 Oct 2026).
- **Operation sequence and synchronisation map.** The ordered operations of each arm, the positions and mechanisms of its GPU-to-CPU synchronisations, and the estimator's selection (its masks on each recorded prompt). Recorded per **code path**: GPU architecture, library versions, and which implementation runs (for example, XAttention's scoring uses Triton on the A100 and H100 and PyTorch elsewhere). A code path already traced is reused (the L4 PyTorch path from P1). A new code path is recorded on the target by a **structural probe**: each arm runs once at short contexts (2048 and 4096 tokens; a chunked arm at three probe lengths, each with at least two chunks) under the profiler, the order of operations and synchronisations is kept and every duration discarded, and the sequence is extended to the target length by the arm's chunking rule, checked by agreement between the short contexts. Where the result is "different", the arm's full-length structure is recorded on the target under the profiler, with every duration discarded (Appendix A, 27 Oct 2026). The checker classifies each pairing and arm as "same sequence" or "different sequence" under a strict definition (primary) and a looser one (secondary, reported beside it) (Appendix A, 25 Oct 2026); H0 and H2 compare components only within the same sequence under the strict definition. The strict definition compares, in order, each operation's class (its kind, with a synchronisation's mechanism and a copy's direction), its stream (by order of first use), whether the host blocks on it, and its payload class (none, or a class set by the edges in T4.1's list, proposed 8 B, 4 KiB and 1 MiB); kernel names, aten operators and layer labels are not compared. The pairings each hypothesis is scored on are listed in the lock file and printed with the lock table (Appendix A, 31 Oct 2026). The **estimator's selection** is recorded per code path at the grid lengths, untimed, since density depends on length and the short probe cannot give it. P1's masks serve the L4 PyTorch path. On P2 both XAttention code paths run on the same card through the existing `use_triton` argument (the mask gate, Section 7); masks are recorded on the target only for the first card of a new code path, and only if that gate fails (P4 is itself a new code path, Hopper with Triton: its structural probe and its mask recording run on P4, untimed, whatever the P2 gate's result). P4's recorded Triton masks are compared with P2's: if they differ, P6 records its own masks and the full-transfer claim (H2) is restated.
- **Recall.** At a layer, the share of that layer's dense attention mass, computed from its actual inputs in the arm's own forward pass, that the kept blocks capture (primary). Recall against a separate dense pass (whose scores are already cached) is a secondary measure. H4 is read on the primary one.
- **Accuracy.** Paired non-inferiority against dense (test in Section 5.7).
- **Admissible configuration.** Dense, or an arm at a density whose accuracy is non-inferior to dense (Section 5.7). Admissibility comes from accuracy measured once on the L4 (the primary GPU, Section 5.7), or from recall if H4 holds; it is not re-measured per pairing. It is a decision input, not a confirmatory claim (Section 5.7). It transfers to a pairing on another code path only if the mask gate passes (Section 7). **Per-arm rule for H6** (Appendix A, 27 Oct 2026): the restriction applies per arm, not per pairing. If the gate fails, only the arms it tests (the XAttention arms, eager and compiled, as shipped and with their checks removed) lose the L4's admissibility on the new code path. On those pairings they are removed both from the dispatcher's choices and from the best measured admissible configuration that regret is measured against, and every arm the gate does not test keeps the L4's admissibility. H6 is then still scored on P2 and P4 over the remaining arms, and the restriction is reported per pairing, naming the arms removed.
- **Kernel-speedup rule.** The decision a practitioner would make from published results: use an estimator at its admissible density wherever its sparse kernel alone beats the selected dense kernel on that GPU, ignoring estimator, host and synchronisation costs. Kernel times are device components, so the rule uses no input the model lacks.
- **Profitable.** End-to-end speedup above 1 over the fastest correct dense kernel, at non-inferior accuracy, estimator cost included. **Predicted profitability** on an unmeasured pairing combines the time model with the admissible density per estimator: from recall if H4 holds, otherwise from that estimator's accuracy runs.

### 5.3 Per-pairing session protocol

1. **Environment.** One container image across providers; driver matched where possible and recorded; threads pinned to the GPU's NUMA node; CPU frequency sampled; clocks locked where permitted and recorded; GPU clocks and throttle reasons sampled during every timed block.
2. **Host-speed probe** (fixed single-thread loop plus null-kernel launch burst) at the start, middle and end of the session and between ground-truth blocks.
3. **Link microbenchmarks.** Bandwidth both ways, pinned and pageable; s_fixed per synchronisation mechanism at the smallest payload, with the device idle (Section 5.1); PCIe generation and width; bandwidth under a concurrent CPU load sized like the largest mask build of any arm at each context length; launch-queue depth Q. Then the **structural probe** for any arm whose code path has not been traced (Section 5.1); durations discarded.
4. **Host components.** Operation sequence with null kernels; CPU-side compute at target sizes.
5. **Device components.** Every arm's kernel sequence replayed in order as a CUDA graph (masks and shapes recorded per code path, Section 5.1; data-dependent work replayed with each prompt's recorded mask). Every operation also replayed in isolation as a cross-check.
6. **Prediction committed.** Computed from steps 3 to 5 (plus transferred components for H2), written with its sha256 and synced. Each prediction in the file is keyed by model, code path, arm, density, context length and batch (Appendix A, 25 Oct 2026).
7. **Ground truth.** Untraced end-to-end prefill per arm, density (a set fixed at lock that includes every admissible density, so every configuration the dispatcher can choose is measured), context length and batch, arms interleaved, with a dense control. Every deployable arm's timed region includes its estimator, mask build, copies and synchronisations; the oracle arm may use cached scores, and its rows are labelled a non-deployable reference (scoring cost outside the timed path) (Appendix A, 26 Oct 2026; label corrected 27 Oct 2026). Median, p90 and p99 over repeats are reported. Every row carries its context length, batch, mask density, executed density and builder kind (`gt_schema`); a row without them is refused by the harness and by every reader. The builder kind, "cpu" or "gpu" (none for dense), is where the row's timed mask construction runs, and the harness holds the declared kind to what its probe saw in the timed blocks (Appendix A, 31 Oct 2026). **Context grid:** 2048, 4096, 8192, 16384 and 32768 tokens for every arm, balanced across arms; nothing above 32768, since the Qwen2.5 models stop there and Llama-3.1-8B does not fit at 65536 on an L4. Each cell is checked at lock against the model's position limit. **Grid rule for accuracy runs:** a cell's prompt plus its task's generation cap must be within 32,768 positions, so no row can decode past the trained positions; a cell that does not fit is sized down, never run past the limit (Appendix A, 27 Oct 2026). At 32768, admissibility is taken from the accuracy cell sized to 32,768 minus the task's generation cap, while the timing cell stays at 32768; each such pair is named in T4.1's list. 2048 and 4096 are **model-validation points, not operating points**: they test the model where host work and synchronisations are the largest share of runtime, and check the structural probe's extrapolation against measured time. No profitability claim is made there, and H6 is scored only at 16384 and 32768. Timed short lengths cost like any other cell, since the structural probe discards its durations. The cell count is controlled on the arm-and-density cross, not on length: compiled variants that T2.21's graph-break report shows identical to another variant are not timed separately; the precomputed-mask ablation runs only at admissible densities and at batch 1 (Appendix A, 27 Oct 2026); window and dense each run at their single density. If the budget still forces cutting lengths, the full grid stays with the XAttention pair, the compiled XAttention pair, mean-pool and dense, and other arms take 8192, 16384 and 32768.
8. **Profiler overhead.** Traced vs untraced end-to-end time per arm.

### 5.4 Cost model

For one CUDA stream, operation i has host cost h_i = c_host(i), device cost d_i = c_dev(i) (GPU execution only) and link cost l_i = c_link(i) (copy time; zero for a kernel). H_i is when the host has issued operation i; D_i is when the device finishes it.

```
H_i = H_(i-1) + h_i
if Q launches are pending:   H_i = max(H_i, D_(i-Q))          (finite launch queue, Q measured per pairing)
if operation i is a synchronisation:  H_i = max(H_i, D_(i-1)) + s_0(m_i, payload_i);  D_i = H_i   (l_i = d_i = 0)
otherwise:  D_i = max(H_i, D_(i-1)) + l_i + d_i                  (l_i at the loaded bandwidth where the operation sequence puts a copy alongside host-side estimator work)
end-to-end prefill time = D_N = H_N   (every sequence ends with a closing synchronise)
```

For a synchronisation h_i = 0: s_0 holds its whole host cost, and the recursion refuses anything else (Appendix A, 22 Oct 2026).

Only device costs transfer between hosts (H2); link and synchronisation costs are always measured on the target pairing. Copies and kernels on one stream are serialised. **Scope:** "one stream" means the GPU executes its own work in order; host and GPU still run asynchronously, and the recursion models that overlap (the host runs up to Q launches ahead of the device, and waits only at synchronisations). Every arm here issues its GPU work on one CUDA stream, which T2.3 checks from the stream IDs in the traces. Claims do not extend to implementations that spread one forward pass over several GPU streams. Contention is costed from the loaded-bandwidth microbenchmark on the target, never fitted and never taken from the workload. It inflates only transfer terms (l_i, and the payload term of s_0), never host costs, so host-memory pressure is charged once. Each pairing's ground-truth trace is checked afterwards for copy-kernel concurrency and unified-memory faults, as a check on the model, never as an input.

**Baselines from the same components.**

- **Sum:** sum(h) + sum(l) + sum(d), no overlap.
- **Fitted sum:** a·sum(h) + b·sum(l) + c·sum(d), with a, b, c ≥ 0 fitted on the same rows as the learned baseline (see Fitting the baselines below). It uses the recursion's inputs with minimal fitting and no structure, so it is the fair test of G1 and the primary comparison: beating only LightGBM, which trains on at most six pairings, would not show that the structure helps.
- **KernelSight-style step form:** our construction from KernelSight-LM's Eq. 4, without the term ℓ the authors leave undefined: max(sum h, sum l + sum d) per layer, plus every synchronisation cost as a serial tail. It differs from the recursion only through operation order, synchronisation positions and the queue term, so the gap between the two isolates G2.
- **Learned (CTFusion-style LightGBM):** task features (context length, density, batch, operation and synchronisation counts), hardware microbenchmark features (host, link, device costs; pinned and pageable bandwidth) and bottleneck ratios (arithmetic intensity per operation class, host-to-device time ratio, transfer demand relative to link bandwidth, synchronisations per operation); trained as in Fitting the baselines below; features and hyperparameters fixed at lock. Tests whether the structure adds anything over regression (G1; secondary comparison). A learning curve reports its error when trained on 1 to 6 pairings, to show whether it is short of data or simply worse.
- **HDBI** reported as a diagnostic only. Its boundedness is one threshold, fitted on the training pairings by sign agreement, with ties going to the lower value, and recorded at lock (Appendix A, 25 Oct 2026).

- **Constant host cost:** the recursion with every host cost replaced by one per-host constant (the median null-kernel launch cost). Tests whether per-operation host costs matter.
- **Nearest measured pairing:** the measured end-to-end time of the most similar pairing already run (same GPU if one exists, otherwise same host platform), unscaled. A naive baseline the model must beat to be worth building.

**Fitting the baselines.** The fitted sum and the learned predictor make committed predictions the same way the recursion does. Each prediction for a pairing is trained only on pairings whose ground truth was banked before that prediction is written, and it is hashed and synced with the recursion's prediction before the workload is timed (K9, T2.11). In the planned run order P2 is predicted from P1 alone and P4 from P1 and P2. The training set is whatever has been banked when the prediction is committed, and each prediction file records it. The analysis checks both directions: every pairing banked before the prediction was written is in its training set, and none banked after it is; a pairing banked within the allowed clock skew of the write is refused as unorderable (Appendix A, 31 Oct 2026). The learned predictor's committed prediction for P2 is trained on one pairing and sees no variation in its hardware features; its learning curve (T2.10) and the retrospective fits show how much this matters. These committed predictions are the ones H1 scores. Full leave-one-pairing-out fits, trained on every other pairing including those run later, are reported as a retrospective secondary analysis, labelled as such, because a forecaster could not have had the later pairings. Gate A (T3.3) stays at the sum and the KernelSight-style step form, because on P1 no other pairing exists to train a fitted baseline.

**Reported for every prediction:** absolute relative error; decision error (predicted profitable when it is not, and the reverse); crossover-length error; and a prediction interval from bootstrapping the component measurements. Errors inside the noise floor (Section 5.6) are not interpreted. A predicted tie is "not profitable" (dense) in both decision error and sign agreement; cells whose measured sparse-minus-dense difference is inside the resolution floor stay unscored by both, whether or not the sparse configuration is admissible, and are reported separately (Appendix A, 26 Oct 2026; confirmed 27 Oct 2026).

**Model ablations** (from the same components, no extra runs): the recursion without the synchronisation term; host-only (sum h) and device-only (sum l + sum d) lower bounds; the queue sensitivity below.

**Batch.** Batch 1 and 4 at 16384 on the L4 pairings; batch 4 at 32768 where memory allows on the A100 and H100. Sparse arms are evaluated at batch 1; batch 4 holds dense only, and a sparse arm above batch 1 is future work (Appendix A, 1 Nov 2026).
**Crossover.** Sparse is profitable where D_N(sparse) < D_N(dense). The crossover is reported as the bracket between adjacent grid lengths where the sign of sparse minus dense time changes, widened by the bootstrap interval of the difference at each endpoint; the same rule is applied to predicted and to measured times. A quadratic fit a·L² + b·L + c per arm is a secondary point estimate, reported with its residual (a form that fits dense well and sparse poorly is itself a finding). No crossover in range is reported as such, a location inside the resolution floor is not interpreted, and two crossovers are possible. **Crossover error:** when the predicted and the measured result have the same number of brackets, each pair is compared in order by whether the measured bracket lies inside the predicted one, whether they overlap, whether the direction of the sign change agrees, and the shift between their centres in grid steps; otherwise the result is reported as missed, spurious, a different count, or unresolved (Appendix A, 25 Oct 2026).
**Queue sensitivity.** Every committed prediction is recomputed with Q at 0.25x, 0.5x, 2x and 4x the measured value, and with no queue term.
**Density sensitivity.** Every committed prediction is also recomputed at plus and minus the measured cross-path density difference (the mask gate, Section 7; T2.28).

### 5.7 Quality measures

- **Accuracy test (pre-registered):** exact paired non-inferiority, one-sided alpha 0.025, as used in the pilots: a union bound over one-sided Clopper-Pearson bounds on the two discordant cells (`attnbench/analysis/exact_noninferiority.py`). The dense arm must reproduce exactly in every run on the same card.
- **Primary accuracy statement:** the achieved one-sided lower confidence bound on the paired accuracy difference, in points, reported continuously. The margin is used only to produce the admissibility label the dispatcher consumes: 10 points primary, with sensitivity at 5 points. No 2-point column: with no discordant pairs the union bound's floor is 4.3 points at n = 100 and 2.2 at n = 200, and about 220 examples are needed for 2 points. Absolute and relative differences are both reported (K7).
- **Margin against speedup:** for each margin and configuration, whether it is admissible and the speedup it buys, reported as a frontier from the same accuracy rows (no GPU cost).
- **Primary cell size:** `qa_1`/16384 is sized once at n = max(200, the H4 power rule), so the same rows serve admissibility and H4. At 200 the 5-point label is reachable at moderate discordance. Secondary cells keep the 10-point margin, stated as such. Admissibility n is fixed at lock.
- **Admissibility family:** admissibility is a decision input, not a confirmatory claim. Its Holm family is declared at lock as every admissibility test that feeds the dispatcher. Correcting shrinks the admissible set, which can move regret either way, so dispatcher regret is reported with and without the correction.
- **Replacement test:** a more powerful paired test is adopted only if simulation shows coverage at or above nominal across dense accuracies including the near-ceiling region and across the pilots' discordance rates, with power secondary among tests that pass coverage. The choice is recorded in the lock commit. Candidates are leads only until read in full (rule 5).
- **Recall:** both references (Section 5.1), per layer, on the very masks that produced each accuracy row; also by head type (retrieval-like vs local, criterion fixed at lock) and by depth third.
- **Intrinsic recall:** budgets 0.50, 0.25, 0.10, 0.05; null scorer as a floor; budget selection on 32 examples per task.
- **H4 across block sizes:** on the primary cell (`qa_1`/16384; n as in the primary cell size above), block sizes 32, 64 and 128 through an untimed reference masked-attention path; block 16 only if that path supports it.
- **Recall matching:** an estimator reaches a target recall only through its own budget settings (threshold, top-k or density), never by editing its masks. The share of rows that find a match is reported.
- **H4 equivalence bound:** justified at lock from the tasks (how large an accuracy difference would change which estimator a practitioner picks). The default is 10 points; T1.5 also prices a 5-point bound, which needs about four times the examples.
- **H4 power rule (fixed at lock):** n ≈ (z(1-α) + z(1-β/2))² × p / δ², where p is the rate at which two estimators disagree on an example (measured on the banked pilot rows, T1.5), δ is the equivalence bound, α is the one-sided level for each of the two tests and 1-β is the power, all fixed at lock, with α adjusted by Holm across the confirmatory family. p is the upper 95% confidence bound of the pilot disagreement rate, not its point estimate. At α = 0.025, 90% power and δ = 10 points this is about 1,300 × p (130 at 10% disagreement, 260 at 20%). Bonferroni over three comparisons gives about 1,630 × p, and Holm needs no more than Bonferroni; the family size, and so n, is fixed at lock. The exact test needs more.
- **H4 confirmatory family:** the planned estimator pairs at block sizes 32, 64 and 128 on the primary cell, plus the random-selection control against each estimator, Holm-corrected together. Head type and depth thirds are exploratory and spend no α. An H4 result below the fixed power is reported as inconclusive, never as support or refutation.
- **Where measured:** once, on the L4 (the primary GPU), with the dense control repeated on the A100. The cross-card control's acceptance criterion is a task-score bound fixed at lock, with the exact-match rate reported alongside; bitwise reproduction across cards is not expected.
- **Position limit:** every accuracy run follows the grid rule in Section 5.3 step 7 (prompt plus generation cap within 32,768 positions). Banked 32768 rows that broke it are confounded: every NIAH row at 32768 and about a fifth of `qa_1` rows there decoded past the limit (`docs/t4_xattention_calibrated.md`), so the `niah_multivalue`/32768 collapse is not a finding (Appendix A, 27 Oct 2026).
- **Dense floor (K7)** and **critical density** (lowest non-inferior oracle density; descriptive only).

### 5.8 Extension: chunked prefill

On P5, with inline mean-pool and calibrated XAttention, prefill also runs in chunks of 2048 and 4096 tokens at 16384 and 32768. Each chunk reruns the estimator over the accumulated keys, which the recursion represents as repeated operations; the predicted re-selection overhead is committed first. First check whether the block-sparse kernel supports query chunks shorter than the key length; if not, drop the extension and record it. The kernel's time at each query-to-key ratio is recorded separately from the per-chunk estimator operations, and mask density separately from executed density. This reruns the estimator per chunk and is not presented as state-of-the-art chunked-prefill engineering. External reference only: CompactAttention reports XAttention at 0.68x to 0.84x of dense speed end to end under chunked prefill on two GPUs.

### 5.9 Application: profitability dispatcher

**What it decides.** For each pairing, context length and batch, one configuration: dense, or a sparse arm (eager or compiled) at one of its admissible densities. Sparse arms are evaluated at batch 1, so above batch 1 the choice is dense by construction and is not scored (Appendix A, 1 Nov 2026). It picks the admissible configuration with the shortest predicted end-to-end time, and dense unless a sparse configuration is predicted faster by more than the resolution floor.

**Inputs.** Only what a prediction may use on an unmeasured pairing (Section 5.1), plus admissibility. The choice is written into the same hashed prediction file as the time prediction, before the workload runs (K9).

**Scoring.** On each held-out pairing, from the measured ground-truth grid (Section 5.3, step 7), so it needs no extra GPU sessions: regret (H6), decision errors (sparse chosen where dense was faster, and the reverse), and time gained or lost against always-dense.

**Comparators.** The kernel-speedup rule (Section 5.1; primary), always dense, always the sparse arm with the best kernel speedup, and the best measured choice on the nearest measured pairing.

**Scope.** An offline decision per pairing, context length and batch, not a runtime scheduler that reacts to live load (Section 10).

## 9. Known risks

- **Small panel.** Seven pairings; claims are limited to the measured host platforms and GPUs.
- **Limits stated in advance.** Batch 1 and 4 only, with no extrapolation to larger batches. One CUDA stream. G3 is a controlled study scoped to the tested models, tasks and block sizes, not a general law. The chunked-prefill extension is not representative of state-of-the-art chunked prefill.
- **Structural probe may miss length-dependent branches.** Checked by agreement between its two short contexts; a disagreement means the arm's sequence is taken as "different" for H0 and H2.
- **Separability may fail** (Gate D).
- **The whole-process `-O` control is not run** (Appendix A, 12 Oct 2026), so no claim is made about the size of `-O`'s effect on the rest of the process. The isolation of the asserts-removed arm rests on what the instrument does, verified in every session, not on an estimate of what it leaves behind: the hook compiles exactly one package with asserts stripped and logs every module it compiled; the bytecode check confirms that only assert sequences and `__debug__` blocks disappeared from that package; the hook's log matches the `xattn` package and `sys.flags.optimize` is 0, so every other module keeps its asserts; and the default arm is checked to still carry XAttention's asserts.
- **One code-path mismatch with three faces.** XAttention's thresholds were calibrated on the A100's Triton path (T1.1 amendment A4) and are applied on the L4's PyTorch path, where admissibility is measured and from whose masks device costs may be replayed, while the A100 and H100 run the Triton path. The mask gate (Section 7) measures the mismatch, the density sensitivity (Section 5.4) bounds its effect on predictions, and admissibility transfers only if the gate passes.
- **Component profiling may misstate composed behaviour.** Null kernels can understate host cost; in-order graph replay keeps cache state between kernels but not host-induced gaps, and isolated replay (the cross-check) removes cache effects; TaxBreak notes replay is imperfect for synchronisation-heavy kernels, which describes our sparse arms. H1's error on real pairings measures how much this matters.
- **Implementations may remove the synchronisations G2 prices.** Fused, synchronisation-free estimators exist (VSPrefill). On them the model should predict no gain over simpler forms, which is a correct prediction, not a failure; the paired XAttention arms show what the synchronisations cost where they exist. Compilation with capture options may also remove some; the compiled arms measure this, and compiled variants with no wait left are predicted the same way.
- **Profitability may be empty for deployable estimators.** In the pilots none was non-inferior at any tested density. The primary claim is time prediction at a given density.
- **The dispatcher may only tie always-dense.** If no sparse configuration is admissible and faster, its value is in avoiding the kernel-speedup rule's losses, and that is the claim then.
- **A fitted baseline may win.** Each committed prediction of the fitted sum and LightGBM is trained only on the pairings banked before it: one pairing for P2, at most six for the last pairing run. The retrospective leave-one-pairing-out fits train on up to six. Either result is reported, on held-out pairings only.
- **G3 may be partly pre-empted.** Oracle-guided sparse prefill plans to measure recall of oracle support by its learned indexer. H4 is the cross-estimator test; that is how it is positioned if their follow-up appears first.
- **H4 may fail.** That is a result.
- **Cloud hosts are not controllable.** A frequency difference between sessions is the first candidate explanation for any H0 failure.
- **Two providers** add operational risk (Gate C).
- **Sparse speedups are small on the primary model.** The claims concern prediction.

## 10. Out of scope, and rejected alternatives

**Out of scope:** models needing more than one GPU; decode sparsity; natively trainable sparse attention; continuous batching and batch above 4; chunked prefill beyond Section 5.8; synthetic host speeds as evidence (delay injection only as an instrument check); a new estimator as a headline; timed kernels below block 128; cross-attention; linear attention; contexts above 32768; model families beyond Qwen2.5 and Llama-3.1; a runtime scheduler that reacts to live load.

| Rejected | Reason |
|---|---|
| A head-adaptive or entropy-driven estimator as the contribution | Already explored (FlexPrefill and Twilight, from abstract; AB-Sparse) |
| Recall by block size per head as a contribution | AB-Sparse reports it; kept as control K5 |
| Benchmarking estimator cost against quality | Method papers and CompactAttention already report it |
| Oracle masks as a quality ceiling | An attention-mass oracle is a reference, not a task optimum (oracle-guided sparse prefill; The Sparse Frontier) |
| An analytical sparse-kernel model carried across GPU generations | KernelSight-LM finds attention-kernel efficiency transfers poorly across GPU generations ("limited cross-generation transfer", its Section 8); device costs are measured |
| A fitted contention penalty | Would be tuned on the outcomes it predicts |
| A serving simulator as the baseline | Both simulators use per-device profiles and model no host work inside a step; the learned predictor and the KernelSight-style step form are fairer comparators |
| Q sensitivity over {4, 8, 16} | Far below the measured queue scale; sensitivity is relative to measured Q |
| PLA's depth-wise concentration as evidence against H4 | H4 already matches recall per layer; depth is reported as a stratum |
| A bare-metal control pairing (suggested by a reviewer) | Over budget, and the claims concern cloud hosts; the noise floor is reported instead (Section 5.6) |
| A second full-transfer pairing | Needs a new pairing; P7's host and GPU appear nowhere else, so it cannot be one. P6 stays the single full-transfer test, reported as such |
| H4 at one block size only | How recall behaves across block sizes is part of G3; the Holm family handles the extra comparisons |
| A multi-stream arm | Out of scope; the single-stream boundary is stated instead (Section 5.4) |
| Narrowing the study to G3 alone (suggested by a reviewer) | The researcher judges G2 and G3 both genuinely open (5 Oct 2026); both stay in scope |
| Dropping the fitted sum as physically unjustified (suggested by a reviewer) | Having no structure is its purpose: it is the control that shows whether structure helps |
| A runtime scheduler that routes requests by live host load (suggested by a reviewer) | Needs a serving system and a model of live load; the dispatcher decides offline per pairing, context length and batch (Section 5.9) |
| Dropping the constant-host-cost baseline (suggested by a reviewer) | Costs no runs, and tests whether per-operation host costs matter |

## Appendix B. Glossary

**Arm:** one way of producing masks (or dense attention), timed and scored identically. **Estimator:** the part of an arm that decides which blocks to keep. **Density:** fraction of blocks kept; *executed* density can differ from *mask* density after unions. **Crossover:** the grid bracket in which the sign of sparse minus dense time changes on a pairing (Section 5.4); there may be none or two. **Noise floor:** the between-session spread of end-to-end time (P1 repeats). **Resolution floor:** the smallest sparse-minus-dense difference interpreted, set from the within-session spread of that difference. **Regret:** how much slower the dispatcher's chosen configuration is than the best measured admissible one. **Graph break:** a point where `torch.compile` stops one compiled graph and falls back to Python before starting the next. **Pairing:** one host CPU platform with one GPU model on one provider. **Mask-rule era:** a period during which the mask rule was unchanged; results from different eras are not pooled.
